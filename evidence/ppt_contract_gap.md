## Executive Summary

An exhaustive audit of `app/engine/exports/ppt_pack.py` against `docs/12_POWERPOINT_OUTPUT_SPEC.md` §3.6 and the freshly landed template `packaging/templates/FPAMonthEndCopilot_v1.pptx` (36,131 bytes, 7 layouts, 103 named shapes generated by `scripts/make_pptx_template.py`) establishes the following truths:

1. **Zero Template Opening / Zero Named Shape Resolution:**
   `app/engine/exports/ppt_pack.py` does **not** open the template file, inspect slide layouts, or resolve shapes by name. At line 290, it calls `prs = Presentation()` without arguments, creating a blank presentation in memory, and builds 100% of the slides from scratch using python-pptx blank layout `6` (`prs.slide_layouts[6]`).
2. **Total Absence of `ERR-EXP-014`:**
   Error code `ERR-EXP-014` ("template damaged / missing named shape") is completely unimplemented (0 occurrences across `app/` and `tests/`).
3. **Template Independence & Voiding of Parity Evidence:**
   PowerPoint generation succeeds identically regardless of whether the template is a 16-byte dummy ASCII placeholder (`PPTX_PLACEHOLDER`), the newly authored 36 KB binary template, or missing altogether. Consequently, prior reports claiming "100% Engine/Excel/PPT parity against the template contract" only proved that python-pptx can read back what `ppt_pack.py` procedurally drew on a blank canvas.
4. **Name-Delta Analysis:**
   Because `app/engine/exports/ppt_pack.py` has **no resolver at all**, the engine actively expects **0 template names**, while the template provides **103 named shapes**. Conversely, when mapped against Doc-12's catalog, the template implements 103 shapes including 4 disclosed assumptions, while `PPT-004_driver_5600` was correctly omitted.
5. **Geometry Spec Defect (Doc 12 Line 541):**
   Doc 12 line 541 specifies `"0.45, 1.45, 12.43, 3.60 (7 rows x 0.60in)"`, which is mathematically contradictory ($7 \times 0.60 = 4.20 \ne 3.60$). If total height were 4.20in, the table would end at $y = 5.65\text{in}$, which fits before the footer at $y = 6.90\text{in}$. However, `ppt_pack.py` line 894 hardcodes table height to `3.80` inches ($y=1.50$ to $5.30$), disagreeing with both 3.60 and 4.20.

## 6. Review of Doc 12 Line 541 Geometry Contradiction

### 6.1 Verbatim Specification Contrast
- **Doc 12 Line 541:**  
  `` `PPT-004_table` | Table | 0.45, 1.45, 12.43, 3.60 (7 rows x 0.60") ``  
  *Arithmetic:* $7 \times 0.60 = 4.20\text{ in} \ne 3.60\text{ in}$.
- **Doc 12 Line 579:**  
  `` `PPT-005_table` | Table | 0.45, 2.58, 12.43, 3.24 (6 rows x 0.54") ``  
  *Arithmetic:* $6 \times 0.54 = 3.24\text{ in}$. (Internally consistent).

### 6.2 Geometric Tiebreaker Analysis
- For `PPT-004` (Slide 4 - Top Variances):
  - Table top: $y = 1.45\text{ in}$.
  - Narrative box top (line 542): $x = 0.45, y = 5.20, w = 12.43, h = 1.40$.
  - Narrative box bottom: $5.20 + 1.40 = 6.60\text{ in}$.
  - Footer top (line 485 / standard): $y = 6.90\text{ in}$.
- **Collision Check:**
  - If Table height = **4.20 in**:  
    Table bottom = $1.45 + 4.20 = \mathbf{5.65\text{ in}}$.  
    This **collides directly with the Narrative Box** which starts at $y = \mathbf{5.20\text{ in}}$! A 4.20 in table overlaps the narrative box by 0.45 inches.
  - If Table height = **3.60 in**:  
    Table bottom = $1.45 + 3.60 = \mathbf{5.05\text{ in}}$.  
    This leaves a clean $0.15\text{ in}$ gutter before the Narrative Box at $y = 5.20\text{ in}$.
- **Conclusion:** The explicit height of **3.60 in** is the geometrically correct boundary. The annotation `(7 rows x 0.60")` was an authoring typo for 7 rows fitting within 3.60 in ($3.60 / 7 \approx 0.514\text{ in}$ per row). The template author's decision to enforce 3.60 in with 0.514 in rows is geometrically sound.
- **Engine Comparison:** `app/engine/exports/ppt_pack.py` line 894 hardcodes table creation at:
  ```python
  table_top = Inches(1.50)
  table_height = Inches(3.80)
  ```
  This ends at $y = 5.30\text{ in}$, colliding by 0.10 inches with a narrative box at 5.20!
