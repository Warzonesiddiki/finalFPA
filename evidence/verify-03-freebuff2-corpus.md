## 2. The defect: "regenerate from one command" is true, but the committed corpus is
not what that command produces

HO-036's headline is that the corpus is reproducible from a single command. Measured
against the committed tree:

```
REGENERATED vs COMMITTED: identical=1 differing=7
  DIFF bank_ledger_actuals.csv              committed 18236a432c2bc4d8 vs regenerated b1bd7fd9fe0472c5
  DIFF budget_fy26.csv                     committed 93334096f4fdaf77 vs regenerated af0cd85872eeddd5
  DIFF d365_gl_actuals.csv                 committed 199c5e6aaa07452f vs regenerated 16a0a4dc592d8c3c
  DIFF import_history/01_bank_batch_037.csv committed cfda2b7f19674cc4 vs regenerated 9bd938aff4dcb5f7
  DIFF import_history/03_bank_batch_040.csv committed 2f899e511b0fc5e0 vs regenerated 2ef1314edc64b578
  DIFF import_history/04_bank_batch_041.csv committed 1e1b2648790d87d7 vs regenerated 33c24b3deaaa4895
  DIFF payroll_procurement_actuals.csv      committed 37f462a146bb78b3 vs regenerated f2d1c2d63c055d3b
  committed-but-not-regenerated: ['test_comment.csv']
```

**Seven of eight CSVs differ.** `test_comment.csv` is not regenerated by the generator
at all; it is a hand-maintained fixture, so its absence is expected and is not counted
as a drift.

Two distinct causes, separated deliberately so the finding is not "the corpus is
broken":

**Cause 1 — line endings only (3 files, benign).** The `import_history` CSVs are
identical once CRLF is normalised to LF:

```
file                                             raw   lf-norm  committed CRLF  regen CRLF
import_history/01_bank_batch_037.csv           False     True               6           0
import_history/03_bank_batch_040.csv           False     True              12           0
import_history/04_bank_batch_041.csv           False     True               3           0
```

Both files hold 4 lines for `04_bank_batch_041.csv`; the first "difference" is
`committed CRLF count 3` versus `regen CRLF 0`. A reviewer who diffs these three files
by eye sees a change and concludes the corpus moved. It did not. What this *does* break
is any byte-level checksum comparison between a regenerated corpus and the committed
one — which is exactly the kind of check a reproducibility gate wants to run, so it is
worth recording rather than dismissing.

**Cause 2 — real content drift (4 files, substantive).** `d365_gl_actuals.csv`,
`budget_fy26.csv`, `bank_ledger_actuals.csv` and `payroll_procurement_actuals.csv`
differ after normalisation. The GL header is the clearest evidence:

```
committed hdr: '...,ProjectType,DocumentDate'
regen     hdr: '...,ProjectType,DocumentDate,JournalCategory'
```

The generator emits a `JournalCategory` column the committed corpus does not have.
That column is load-bearing, not cosmetic: `JournalCategory` is read at
`app/engine/rules/rules_17_24.py:603` by EXC-022, and its absence sets
`degraded_category`, which changes the finding text at
`app/engine/rules/rules_17_24.py:749-750` ("journal_category unavailable; evaluated all
GL expense rows"). The sub-ledger feeds diverge earlier than the header — bank row 3
is `21/08/2026 … 11330.00` committed against `05/06/2026 … 34612.00` regenerated, i.e.
different dates and different amounts, not a column addition.

**Why the drift exists, from git rather than inference:**

| commit | date | generator | corpus CSVs |
|---|---|---|---|
| `6b8bc13` | 2026-10-06 02:26 | changed | regenerated (incl. both sub-ledgers) |
| `6a6a9e6` | 2026-10-06 22:17 | changed (271 lines) | regenerated (GL, budget, import_history 037/040) |
| `7e12be8` | 2026-10-06 19:23 | changed (32 lines, adds `JournalCategory` at `GL_HEADER`) | **not regenerated** |

`7e12be8` added `JournalCategory` to `GL_HEADER`
(`sample-data/generate_sample_data.py:167`) and changed `generate_dataset`, and it
regenerated **no CSV** — confirmed by `git show 7e12be8 --name-only`, which lists no
`.csv`. So the generator and the committed corpus diverged at that commit and have
stayed diverged.

**What this does and does not invalidate.** The corpus on disk is internally coherent
and loads: §3 measures that. What is false is the stronger reading of "the corpus is
reproducible from one command" — a reader who runs the documented command overwrites
7 files and gets a different GL, a different budget, and two different sub-ledgers. That
matters because the acceptance evidence in `evidence/` was measured against the
*committed* corpus while the generator describes a different one. HO-036 did not claim
byte-equality with the committed tree (it claimed run-to-run stability, which holds), so
this is not a false claim in the handoff — it is a gap between what the card's headline
implies and what the tree supports. Corrected here rather than left to be discovered by
the next person to run the command.

**Also reproduced, and this one is the more important bar:** the regenerated corpus is
itself perfectly balanced, so this is drift and not corruption.

```
python scripts/verify_trial_balance.py                        -> OVERALL VERDICT: PASS - PERFECT BALANCE  (exit 0)
python scripts/verify_trial_balance.py <scratch>/run1/d365_gl_actuals.csv
                                                              -> OVERALL VERDICT: PASS - PERFECT BALANCE  (exit 0)
```

The unbalanced vouchers printed above that verdict are the planted anomalies (P1, P6,
P8, P19, P21, P24 …) and are diagnostic output by design; `verify_trial_balance.py`'s
module docstring states the file verdict rests on file/entity/period per IMP-023 and
that the voucher section is diagnostic.

## 3. HO-038 (TB-011) — the DEC-056 gate, re-measured

Re-run through `app/engine/imports/parser.py` rather than transcribed from the
handoff. Synthetic probes use real `ParsedTransaction` objects:

```
SYNTHETIC probes (one debit-only row, so net == the value shown):
  amount-style net 0.00 (loads, pass)                  -> pass  offending=0
  amount-style net 350.00 (loads, warn)                -> warn  offending=0
  amount-style net 500.00 boundary (loads, warn)       -> warn  offending=0
  amount-style net 3500.00 (rejects, fail)             -> fail  offending=1
  amount-style net -350.00 (loads, warn)               -> warn  offending=0

  The same numbers through the UNSCOPED balance gate (journal GL path):
  journal GL net       0.00                             -> pass  offending=0
  journal GL net     350.00                             -> fail  offending=3
  journal GL net     500.00                             -> fail  offending=3
```

Every row of HO-038's probe table reproduces, including the two that matter most: the
500.00 boundary loads, and the journal GL path is unchanged.

Real corpus files, net recomputed from the committed CSVs using the column map copied
from `app/engine/imports/profiles.py:155-159`:

```
REAL corpus files, net recomputed from the committed CSVs:
  bank_ledger_actuals.csv              rows= 498 cols=withdrawal/deposit   net=        0.00 tol=500.00 -> pass
  payroll_procurement_actuals.csv      rows= 398 cols=nettotal/(none)      net=        0.00 tol=500.00 -> pass
  import_history/04_bank_batch_041.csv rows=   2 cols=withdrawal/deposit   net=      350.00 tol=500.00 -> warn

AMOUNT_STYLE_SOURCE_TYPES = ['actuals_payroll', 'actuals_procurement']
SUB_LEDGER_RECONCILIATION_TOLERANCE = 500.00
```

HO-038 claimed 498/498, 398/398 and `04_bank_batch_041.csv` at net 350.00 inside the
500.00 tolerance. All three reproduce.

**Two notes on how I got there, because both were nearly false readings:**

1. **Row counts are 498 and 398, not the 499 and 399 a raw line count gives.** These
   files open with a `# SAMPLE DATA — NOT FOR PRODUCTION USE` comment line above the
   header. Counting `wc -l` gives 500 and 400. My first probe read 499 and 399 because
   `csv.DictReader` consumed the comment as a header row. The comment line is not data.
2. **The sub-ledger feeds are not debit/credit shaped, and guessing the columns
   manufactures a fake failure.** `check_imp_023_subledger_reconciliation` sums
   `t.debit` and `t.credit`, but the bank feed carries `Withdrawal`/`Deposit` and the
   payroll feed carries `NetTotal`/`TaxTotal`/`GrossTotal`. Reading literal
   `debit`/`credit` columns that these files do not have yields **net 0.00 for every
   file** — a false green. Reading `TaxTotal` as the credit side yields payroll at
   **net -3,097,822.32 → fail** — a false red, and the one I hit first. The correct
   mapping is profile 2's `column_map` (`profiles.py:155-159`): `withdrawal→debit`,
   `deposit→credit`, `nettotal→debit`, and `grosstotal`/`taxtotal` are `__ignored__`,
   so payroll's credit side is 0 and its settlement reversals arrive as *negative*
   debits. Only that mapping reproduces the handoff's numbers. Worth knowing for anyone
   else re-measuring this: the obvious readings are wrong in both directions.

**HO-038's self-reported oddity is accurate and I could not improve on it.** It states
the payroll audit row reads Debit 0.00 / Credit 0.00 / Net 0.00 despite 398 rows
landing, because profile 2 maps `nettotal` to the debit side only. Confirmed by the
mapping above. The fix is a profile that maps a credit column — profile work, outside
TB-011's scope, and correctly not done silently.

## 6. Next, and who owns it

1. **Regenerate the corpus, or revert `7e12be8`'s generator change.** Owner:
   `freebuff2` (corpus lane) with `buffy`. Until then any reproducibility check that
   compares a regenerated corpus to the committed one fails for a reason that is not a
   bug in the generator, and `evidence/` describes a corpus that no longer matches its
   own source. This is the single highest-value item in this verification.
2. **Decide whether `JournalCategory` in or out.** If the generator is right, the
   committed corpus is stale and the EXC-022 `degraded_category` path is being
   exercised by accident today; if the column is wrong, the generator should lose it.
   Nothing measured here settles which, and it is a spec question (`06` §11 / EXC-022),
   so it is not mine to rule on.
3. **Add CRLF normalisation to any future corpus checksum comparison**, or record that
   checksums are line-ending-sensitive. Three of the seven drifts are line endings alone.
