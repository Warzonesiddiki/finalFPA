## SECTION 3 — ZERO-COMPROMISE PRINCIPLES

1. **Docs before code.** No product code until the full Phase 0 documentation set exists, passes its quality gate, and I have approved it.
2. **The spec is the source of truth.** Any change to behavior goes into the spec + CHANGELOG **first**, then the code. Code never drifts silently from spec.
3. **Deterministic money math.** All calculations, reconciliations, thresholds, and approvals are deterministic code. AI never computes totals, never approves, never posts, never decides.
4. **Offline-first, local-only data.** No cloud storage, no telemetry, no auto-upload. Raw client files stay on the machine.
5. **Traceability.** Every number the user sees must be drillable back to source transactions and to the source file it came from.
6. **Scope discipline.** Build only what is in the approved phase. New ideas go to the backlog/OPEN_QUESTIONS log — they do not get built opportunistically.
7. **Non-technical UX.** Guided workflow, plain-language errors that state the fix, help text, confirmations on destructive actions, a first-run sample project.
8. **"Potential exception," never "error confirmed."** The tool flags suspects for human review; humans decide.
9. **Quality bars are numbers, not vibes.** Every non-functional target (performance, installer size, start-up time) must be stated as a number in the docs and tested.
10. **Boring, testable code.** No speculative abstractions, no frameworks not approved in Section 4, no microservices, no premature plugin systems.

## SECTION 7 — CANONICAL DATA MODEL (seed for doc 03; elaborate it fully)

Grains must be exact; doc 03 defines every column:

- `FactActual` — one row per posted GL transaction (source file, company, fiscal period, posting date, voucher/document, account, cost centre, department, project, vendor, description, debit, credit, net, currency).
- `FactBudget` — one row per budget line (version, scenario, period, account, dimension, amount).
- `FactForecast` — one row per forecast line (version, method used, period, account, dimension, amount, driver ref).
- `DimAccount` (with statement-line mapping), `DimCompany`, `DimCostCenter`, `DimVendor`, `DimProject`, `DimPeriod` (fiscal calendar), `DimMapping` (source→canonical, versioned, approval-flagged), `FactException` (rule, severity, subject rows, status, owner, notes), `FactImportAudit` (file, checksum, row counts, timestamp, balance check result).

**Integrity rules:** raw imported files archived immutably; every fact row links to its import batch; import cannot complete unless debit = credit (or documented tolerance) and row counts reconcile; mappings are data (editable with history), never hardcoded.

## SECTION 8 — CALCULATION RULES (summary; doc 05 must contain the full formal spec)

- `Variance = Actual − Budget`; `Variance % = Variance / |Budget|` with a documented zero-budget handling rule.
- Favorability is direction-aware per statement line type (revenue vs expense vs memo) — define explicitly, with examples.
- Period comparisons: MTD, YTD, PY MTD, PY YTD — against `DimPeriod` fiscal calendar, not calendar months.
- Comparisons happen at the **lowest shared grain**; if budget exists only at GL/month level, the UI must not imply transaction-level budget matching — state this in doc 02/05 and enforce in the UI spec.
- Rounding: compute at full precision, round for display only, document the rule (e.g., 2 dp for INR, 1 dp for %).
- Currency: v1 = single reporting currency per project OR a simple FX-rate table — **decide in doc 05, document it, and do not half-build multi-currency.**
- Forecast methods (all deterministic): locked actuals; remaining-budget; run-rate; 3-month average; manual override — each with a worked example in doc 07.

## SECTION 9 — EXCEPTION ENGINE (summary; doc 06 is the formal catalog)

Seed rules (catalog must reach ≥15, each fully specified): duplicate invoice candidate (vendor + invoice no. + date + amount); unmapped GL account/dimension; inactive cost centre usage; posting-date/period mismatch; unusual negative expense/credit; missing recurring cost (known monthly charge absent); material unbudgeted spend; material variance over threshold (amount AND %); unusual vendor→account combination; import imbalance; potential cut-off issue (posting near period end with document date in prior period); amount crossing approval threshold; out-of-pattern spike vs trailing average; missing expected accrual; orphan dimension (entity without budget).

- Every rule: default threshold, severity (High/Medium/Low), suggested owner role, false-positive mitigation, and a planted sample case with expected verdict.
- Workflow statuses (spec the final list): e.g., Open → In Review → Explained → Corrected → Closed, with owner, timestamped notes, and export.
- UI wording: "Potential exception — requires accounting review." Never "error" or "wrong entry."

## SECTION 10 — AI POLICY

- **Optional, disabled by default.** Bring-your-own key UI: Azure OpenAI preferred; OpenAI-compatible base URL supported. Key stored via Windows DPAPI / Credential Manager, never in plain files.
- **Allowed uses:** draft variance commentary, summarize top drivers, group similar exceptions, suggest (never auto-apply) account/category mappings, draft follow-up messages — each output linked to the evidence rows that produced it, with a confidence indicator.
- **Forbidden:** computing/altering financial totals, approving anything, editing mappings/data, posting, silent decisions, sending raw client data anywhere beyond the configured endpoint.
- **Redaction:** configurable vendor-name/ID masking before any AI call; only the minimum filtered rows needed go in the prompt.
- **Output:** strict JSON schema (commentary, drivers[], evidence_ids[], confidence); prompts stored as versioned template files in the repo; token/cost caps; caching.
- **Offline fallback:** when no key is configured, generate rule-based narrative from the same driver data so the feature still demos offline.
- **UI labeling:** every AI text shown as "AI draft — review before use."

## SECTION B — ADDITIONAL ZERO-COMPROMISE PRINCIPLES (P11–P20)

11. **The monthly rhythm is first-class.** This is a tool that runs every month-end, not once. The spec must cover the recurring cycle: new period opens → import → validate → analyze → exceptions → forecast refresh → pack out → period archived. One-shot data loads are a design failure.
12. **All-or-nothing imports.** Imports run in a staging area and commit atomically. A crash, cancel, or bad file never leaves half-loaded data. Partial batches are detectable and cleanable on next launch.
13. **Nothing is silently discarded.** Rejected/quarantined rows, skipped sheets, dropped columns — all visible in a validation report with counts and downloadable detail.
14. **Versioned everything the user edits.** Mappings, thresholds, master data, forecast assumptions, AI prompt templates: keep history with timestamp + old/new value, and support revert.
15. **Releases are upgradeable.** Every release must state how existing client projects survive an upgrade (schema migration tested on a real prior-version project). A release that can't upgrade is not releasable.
16. **End-user documentation is a deliverable, not an afterthought.** The non-technical client gets a written user guide and in-app help; you get a handover/support doc. Code without user-facing docs fails the phase gate.
17. **Supply-chain hygiene.** Pinned dependencies, license review (no GPL/AGPL in shipped binaries), `THIRD_PARTY_LICENSES.txt`, per-release dependency snapshot (SBOM-lite), `.gitignore` blocks secrets — no API keys ever in the repo.
18. **Treat imported file content as hostile data.** Transaction descriptions, vendor names, and file contents are untrusted input — for validation, for logs, and especially for AI prompts (prompt-injection defense, Section I).
19. **Color is never the only signal.** Variance favorability, severity, and status must also carry +/− signs, symbols, or text so color-blind users and black-and-white printouts stay correct.
20. **Tabletop walkthrough before approval.** Before requesting Phase 0 sign-off, narrate a full month-end day-in-the-life using only the documents: every step must map to a documented screen, rule, or export. Any step with no home = missing spec.

## SECTION F — EXCEL/CSV INGESTION HARDENING (requirements for doc 04)

Real ERP exports are messy; the import spec must handle or explicitly reject each of these **with a plain-language error that names the sheet and cell/row**:

- Title/banner rows and merged cells above the real header; multi-row headers; a `Total`/`Subtotal` row embedded in data; blank trailing rows/columns; hidden sheets; multiple sheets per workbook (profile selects sheet).
- CSV: UTF-8 BOM, Windows-1252 accents, semicolon/tab/comma delimiters (auto-detect with confirmation step), quoted fields containing delimiters/newlines.
- Dates: ISO, `dd-mm-yyyy`, `mm/dd/yyyy`, Excel serials, date-times — one documented per-profile rule; ambiguous formats must be confirmed, not guessed silently.
- Numbers: thousands separators, accounting parentheses for negatives, currency symbols (₹/$/€), trailing `Cr`/`Dr`, text-formatted numbers.
- Fiscal columns arrive as text (`FY26-P09`); financial-dimension single strings like `Dept=100|CC=200` must be split per a documented parsing rule.
- Formulas vs values: read cached values only (`data_only`), documented; error cells (`#REF!`, `#DIV/0!`) reported.
- Enforced limits (row count / file size) with a pre-scan estimate and confirmation; required-column presence; type validation; per-column profile overrides saved for next month.
- **Reject-vs-quarantine decision stated in the doc**: file-level failures (balance ≠ 0, unreadable) reject the whole file; row-level failures quarantine rows to a review sheet with counts — never silent drops.
- Every import produces a **Validation Report** (pass/fail per check, counts, sample of first N offending rows) saved with the batch.

## SECTION H — FINANCIAL-CORRECTNESS ADDENDA (add to docs 05/07)

- **Fiscal calendar fully configurable** (year start, period codes); all period logic derives from it — no hardcoded calendar months anywhere.

## SECTION B — ARCHITECTURE & STACK ADDENDA (goes into doc 09 + new doc 26)

### B.1 Headless engine (non-negotiable)

- `app/engine/` is pure Python: **no FastAPI, UI, or pywebview imports allowed inside it.** All calculations, validations, exception rules, forecasts, Excel/PPT generation live here.
- Ship a CLI: `python -m app.cli <import|validate|bva|exceptions|forecast|export-xlsx|export-ppt|doctor> --project <path>` with documented exit codes and a `--json` output mode.
- The API layer is a thin shell over the engine; tests target the engine directly; future automation (Power BI export backlog, scheduled runs) reuses the same CLI. Violation of this boundary fails code review.

### B.2 API contract (new document `26_API_CONTRACT.md`)

- FastAPI **OpenAPI schema is the single source of truth**; TypeScript types are generated from it (e.g., `openapi-typescript`) — hand-duplicated types are forbidden (contract drift is a build error).
- Standard error envelope for every failure: `{code, message, hint, details[]}` where `hint` is the plain-language next action the UI shows the user.
- Standard list responses: `{items, total, page, pageSize}`; documented filter/sort parameter grammar; routes prefixed `/api/v1/`.
- Document every endpoint: purpose, request/response schema, error codes, permissions (session token), and which screen (SCR-ID) consumes it.
- Contract tests: response fixtures validated against the schema in CI/`scripts/check`.

### B.3 Data-volume rule (browser never sees the raw firehose)

- Aggregation, filtering, sorting, and pagination happen **server-side in DuckDB**. The browser never receives more than one page (default 100–200 rows) or one aggregation result set.
- All grid views are virtualized; drill-through tables paginate; no view loads a full 250k-row dataset into React state. Document this in docs 08/09; test with the scaled dataset.

### B.4 Configuration layering

- **App-level** (machine): AI key/provider, theme, language, data directory, telemetry=off. Secrets live only here.
- **Project-level** (inside project folder): fiscal calendar, currency/units display, mappings, thresholds, master data, branding, rule enablement.
- Precedence documented; project backup zips therefore contain **no secrets**; a project folder is portable to another machine.

### B.5 ADR-002 — pin the remaining toolchain (stop framework flip-flopping)

| Area | Decision |
|---|---|
| Python toolchain | `ruff` (lint + format), `mypy` (strict on `app/engine`), `pytest` + `pytest-cov`, CLI via `argparse` (or `typer` — choose one in ADR-002, never both) |
| Frontend runtime state | TanStack Query for server state, Zustand for UI state — no Redux |
| Routing / tables | React Router; TanStack Table + virtualizer for all grids |
| Frontend testing | Vitest + React Testing Library; **Playwright** for E2E smoke of the golden path |
| Frontend hygiene | ESLint + Prettier; `tsc --noEmit` gate |
| Version pinning | Python `3.12.x` pinned (`pyproject.toml` + `.python-version`); Node LTS pinned (`.nvmrc`); exact pins in lockfiles (`uv.lock`/`requirements.txt` + `package-lock.json`) |
| Forbidden | Any library outside this table and the kickoff stack without a new ADR |

### B.6 One-command scripts (also proof the build is reproducible)

- `scripts/dev` (run app in dev with hot reload), `scripts/check` (format+lint+type+tests+contract tests), `scripts/build` (UI build → PyInstaller → Inno Setup), `scripts/release` (bump version, tag, build, emit SHA-256).
- `scripts/build` must succeed **from a clean checkout** on a documented machine; that clean-checkout build is part of every release checklist (Addon 1 doc 24).
- Development may run on any OS; **packaging evidence always comes from real Windows 11** (Addon 1 Section G.6).

### B.7 Recompute & invalidation semantics

- Derived views (aggregates, BvA, exceptions) are **computed on demand**; no unbounded caches. If any cache is introduced later, its invalidation rules must be documented in doc 09 first.
- Changing mappings/thresholds/master data marks derived results "stale" in the UI until an explicit re-run; the user is never shown silently outdated numbers.

## SECTION D — FUNCTIONAL PRECISION (seed FRs for doc 02)

1. **Exception identity & re-run semantics.** Key = `rule_id + subject_key`. Re-running rules (after mapping/threshold changes) **never wipes workflow state**: open stays open, closed stays closed; re-flagged closed items show a "flagged again" badge, never auto-reopen. Full history per key.
2. **Aging & bulk operations.** Days-open per exception, aging buckets (0–7 / 8–30 / 31+), overdue highlight; multi-select bulk status/owner changes with one audit entry per item; owner auto-assign from cost-centre/account mapping, manual override always possible.
3. **Period status (Open/Closed).** Closing a period locks its actuals: void/re-import into a closed period requires an explicit, warned "reopen period" action, audit-logged.
4. **Re-import guard.** Identical file checksum → blocked with "already imported on <date>". Different checksum with overlapping vouchers → cross-batch duplicate report before commit.
5. **Control-total reconciliation.** Optional control-totals block in the actuals template; validation report compares file totals vs loaded totals vs (if provided) client control totals; variance fails the import or requires explicit acceptance — documented decision.
6. **Budget & forecast file validation.** Duplicate budget lines vs key; negative amounts; coverage matrix (which entity × account × period cells are missing, as %); sum-vs-approved-total check when provided; unmapped-account list.
7. **Three-way view + forecast accuracy.** Actual vs Budget vs Forecast in one view; for closed periods show Forecast vs Actual columns with signed error — formulas in doc 05, view in Analyze, feeds commentary.
8. **Rolling windows.** MTD, YTD, and TTM (trailing 12 periods) where data exists; window labels always visible so no ambiguous "period totals".
9. **One-off / exceptional item tagging.** PRD must decide explicitly: minimal v1 (tag actual rows → "adjusted" toggle views + AI mentions them) **or** park with rationale. Never left undecided.
10. **Rule effectiveness analytics.** Per rule: times raised, % closed as explained, average days to close, last threshold tuning — a tuning dashboard so the engine improves month over month without code changes.
11. **Global materiality setting** (e.g., % of budget or absolute floor) feeding default thresholds; per-rule overrides win.
12. **Export collision policy.** Existing file at target path → prompt (overwrite / keep-both with next `vN`); batch exports follow Addon 1 naming; never silent overwrite.
13. **Evidence bundle.** One click per exception → workbook/zip containing subject rows, relevant validation report, mapping version, and audit trail — ready to send to an accounting team.
14. **Scope decisions the PRD must settle (with defaults):** financial statements in v1 (default: P&L focus; balance sheet/cash flow parked); budget creation in-app (default: import-only); journal-category column (default: optional via mapping profile).

## SECTION C — FEATURE PRECISION PART 2 (seed FRs for doc 02)

1. **AI Mapping Review Queue.** AI may only *propose* mappings: each suggestion carries source column, target field, confidence, and evidence (examples of previously accepted rows). States: `suggested → accepted | edited | rejected`. Accepted mappings apply to future imports; **never auto-applied in the same run**. Bulk accept/edit with audit trail; queue visible on every import using an unprofiled file.
2. **Mapping preview & profile auto-match.** Mapping screen shows the first N rows with detected types and sample values; saved profiles auto-suggest by header fingerprint when a file matches ≥ threshold of known headers; template files carry a **version stamp** and import warns on outdated templates.
3. **Commentary workflow.** Two levels: per-variance-line commentary and a per-period executive narrative (for slide 2). AI drafts are editable; every save versions text (author, timestamp, old→new). Commentary **locks when the pack is issued**; post-issue edits require a re-issue (C.4).
4. **Pack issuance register.** "Issue pack" freezes the underlying snapshot, increments pack version, records date + recipient list, and marks commentary locked. Re-issue creates a new version; issued packs are immutable; exports carry pack version (Addon 1 stamping).
5. **Data-quality score.** Composite 0–100 on the Check screen from weighted validation checks (formula + weights in doc 05) — always displayed **alongside** the individual failed checks so a single score can never mask a failure.

## SECTION G — NUMERICAL TOLERANCE & EDGE-CASE DATA MATRIX (docs 05/02/14)

### G.1 Tolerance policy (doc 05)

- **Internal math:** exact equality at minor-unit precision (Decimal) — no epsilon anywhere in comparisons.
- **Display:** rounding mode defined (e.g., half-up), 2 dp for currency, 1 dp for %; tests assert on display-rounded values using that same defined mode.
- **Cross-artifact:** exact equality of engine values (already required) — UI vs Excel vs PPT vs CLI.
- Forbidding "close enough" tolerance in money paths is a quality-gate item.

### G.2 Edge-case data matrix — every row defined in docs 02/14 with behavior + error message ID

| Input condition | Required behavior (spec must finalize wording/state) |
|---|---|
| First-ever period (no prior periods, no PY) | BvA works; PY/TTM views hidden; run-rate methods disabled with explanatory hint — never a crash or blank chart |
| No budget loaded | BvA screen shows explicit empty state + "Import budget" CTA; variance rules disable with notice — never variance = 0 masquerade |
| Header-only actuals file (0 data rows) | Default: reject with message; allow accept-as-zero only after explicit confirm (zero-activity period) |
| Rows with zero amounts | Kept; excluded from outlier-type rules; visible in drill |
| Future-dated transactions | Loaded per period rule; cut-off exception flags them |
| Dates outside the fiscal year | Quarantined with message — never assigned to a wrong period |
| Duplicate column headers | Import blocked until profile renames them |
| ≥90% rows unmapped | Import blocked with mapping CTA |
| Budget imported mid-period / after actuals | Allowed anytime; stale-derived indicator (Addon 2 B.7) |
| Mixed-currency rows in single-currency project | Decision in doc 04 (default: quarantine with message) |
| Amount exceeding display precision | Round per G.1; never truncate silently |
| Single-row / tiny files | Fully supported (no size assumptions) |
| Amounts in parentheses / `Cr-Dr` / text numbers | Handled per Addon 1 Section F |
